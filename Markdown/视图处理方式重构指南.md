## 一、什么时候用 useRequest

### 适用

| 场景 | 例子 | 模板 |
|------|------|------|
| 表单提交 | Login / Register | 模板 1(manual + refetch) |
| 点击/选择触发请求 | mainpage DirectoryTree.onSelect | 模板 2(manual + 数据加工) |
| mount 时拉首屏数据 | indexview 日历列表 | 模板 3(自动模式) |
| 同组件多个独立请求 | indexview 主请求 + 搜索 | 模板 4(多 hook 实例) |

### 不适用 / 不要硬塞

| 场景 | 用什么 | 原因 |
|------|--------|------|
| 非 HTTP 请求(localStorage / 计算 / 事件) | useEffect / useMemo / 普通函数 | useRequest 是 axios 包装,无价值抽象 |
| 需要乐观更新 / 失败回滚 | 直接 axios + 手动 setState | 当前 hook 不支持 onMutate 阶段 |
| 跨组件共享请求结果 / 长时缓存 | 自己起 context,或引入 SWR/react-query | 当前 hook 只覆盖单组件生命周期 |
| 请求结果驱动后续请求(链式) | 串多次 `await refetch(...)`,或自己写 useEffect | hook 不内置 dependency chain |
| WebSocket / SSE / 轮询 | 自己写 useEffect + setInterval / EventSource | 不是请求-响应模型 |

## 二、调用契约(必读)

`useRequest` 是"克制的最小抽象",有几条隐性 contract 必须遵守,否则会**踩到难以排查的 React 闭包陷阱**。

### contract 1:service 必须用 `useCallback([deps])` 包

```js
// ❌ 错误:每次 render 都新引用,hook 内部 run 跟着不稳
const { refetch } = useRequest((p, { signal }) => api.post('foo', p, { signal }), { manual: true });

// ✅ 正确:service 引用稳定 → run 稳定 → refetch 稳定
const service = useCallback((p, { signal }) => api.post('foo', p, { signal }), []);
const { refetch } = useRequest(service, { manual: true });
```

**何时影响**:把 `refetch` 放进任何 `useCallback`/`useEffect` 的 deps 时(典型场景:回调里用到 refetch,需要 useCallback 稳定回调的引用)。Login/Register 等"事件直调"场景不影响。

### contract 2:`options.deps` 是 mount 自动模式的重跑触发器

```js
// 自动模式:mount + deps 变化都会重跑 run
const { data } = useRequest(service, { deps: [userId] });

// manual 模式:deps 无效, 必须显式 refetch
const { refetch } = useRequest(service, { manual: true });
```

注意:**不能把 `run`/`refetch` 放进 `options.deps`**——它会构成自循环。

### contract 3:`refetch(params)` 返回 `undefined` 表示"已 toast 或被 abort"

```js
const data = await refetch(formValues);
if (data === undefined) return; // 短路,别继续业务流程
// 这里只处理"成功响应"分支
if (!data.backData) { /* 业务态错误 */ }
```

返回 undefined 的两种情况:
- 主动 abort(如组件卸载、并发覆盖)
- 已知错误(已由 hook 内部 `message.error` 提示)

业务代码**不需要再 try/catch**——错误已经被 hook 统一处理掉了。

### contract 4:manual 模式下 mount 不发请求

`{ manual: true }` 时,`loading` 初始为 `false`,useEffect 直接 return。**只有调用方主动 `refetch()` 才会触发**。

## 三、四种迁移模板(可直接 copy-paste)

### 模板 1:表单提交(Login / Register 同源)

**适用**:onFinish / onClick 触发的提交型请求,需要按钮 loading 反馈。

```js
import { api } from '../../server/request';
import useRequest from '../../hooks/useRequest';

const MyForm = () => {
  // service 可以不 useCallback(refetch 没进 deps,无副作用)
  const { loading, refetch: submit } = useRequest(
    (params, { signal }) => api.post('endpoint', params, { signal }),
    { manual: true }
  );

  const handleSubmit = async (values) => {
    const data = await submit(values);
    if (data === undefined) return;       // 已 toast / 已 abort
    if (!data.backData) {                 // 业务态错误
      message.error('...');
    } else {                              // 成功
      navigate('/next');
    }
  };

  return (
    <Form onFinish={handleSubmit}>
      {/* ... */}
      <Button type="primary" htmlType="submit" loading={loading}>提交</Button>
    </Form>
  );
};
```

**配套**:并存的次要按钮(如 Clear)加 `disabled={loading}` 防误操作。

### 模板 2:触发回调(mainpage onSelect 同源)

**适用**:DOM 事件(Tree.onSelect / Menu.onClick / 自定义 callback)触发的请求,**且需要在 useCallback 里包**(因为传给子组件时需要引用稳定)。

```js
const MyView = () => {
  const [detail, setDetail] = useState('');

  // contract 1:service 必须 useCallback
  const fetchService = useCallback(
    (params, { signal }) => api.get('endpoint', { params, signal }),
    []
  );
  const { refetch: fetchDetail } = useRequest(fetchService, { manual: true });

  // 现在 fetchDetail 引用稳定 → onSelect 也稳定
  const onSelect = useCallback(async (keys) => {
    const data = await fetchDetail({ id: keys[0] });
    if (data === undefined) return;
    setDetail(data.describe || 'No description'); // 数据加工后再 setState
  }, [fetchDetail]);

  return <Tree onSelect={onSelect} treeData={...} />;
};
```

**为什么 setDetail 还在**:hook 的 `data` 是**原始响应**,如果业务需要加工(`.describe || 'No description'`),要么在 setState 里做,要么在 service 里做(见模板 3 / 4)。

### 模板 3:mount 自动拉数据(indexview 主请求同源)

**适用**:首屏数据,mount 时一次性拉取。可以在 service 内做数据加工,hook 的 `data` 就是加工后的结果。

```js
const MyView = () => {
  const service = useCallback(
    (_, { signal }) =>
      api.post('list', { from: ts1, to: ts2 }, { signal })
        .then((data) => data.map((item) => ({
          ...item,
          createtime: formatDate(item.createtime),
        }))),
    [] // 静态参数 → 空 deps;若 ts1/ts2 来自 state, 加进 deps
  );

  const { data, loading, error } = useRequest(service);

  if (loading) return <Spin />;
  if (error) return null; // 错误已 toast
  return <List items={data || []} />;
};
```

**关键**:`api.post(...).then(map)` 把"接口适配"塞进 service,等同**最小形态的 service 集中化**——多处复用时再抽到 `src/services/`。

### 模板 4:同组件多 useRequest 实例(indexview 完整模式)

**适用**:一个 view 内有 2+ 独立请求(主数据 + 搜索 / 列表 + 详情等),各自独立 loading/abort。

```js
const MyView = () => {
  const [keyword, setKeyword] = useState('');

  // 主请求:mount 自动
  const mainService = useCallback(
    (_, { signal }) => api.post('main', {}, { signal }),
    []
  );
  useRequest(mainService);                         // 只取副作用,不取 data 也 OK

  // 搜索:点击触发, 独立 loading 状态
  const searchService = useCallback(
    (params, { signal }) => api.post('search', params, { signal }),
    []
  );
  const { loading: searching, refetch: doSearch } = useRequest(searchService, { manual: true });

  return (
    <>
      <Button onClick={() => doSearch({ keyword })} loading={searching}>搜索</Button>
      {/* ... */}
    </>
  );
};
```

**命名**:多个 hook 实例时用 `refetch: 语义化名` 重命名(`doSearch` / `fetchDetail` 等),避免变量名碰撞。

## 四、常见陷阱与解法

| # | 现象 | 根因 | 解法 |
|---|------|------|------|
| 1 | "Maximum update depth exceeded" 死循环 | 把 `run` / `refetch` 放进 `useEffect` 的 deps,且 service 是 inline arrow function | service 用 `useCallback([])` 包(contract 1) |
| 2 | `setState on unmounted component` 警告 | 自动模式但 cleanup 没 abort | 用了 useRequest 就不会有这问题——hook 内已 abort;若仍出现,检查是不是在 service 的 `.then` 里调了外部 setState |
| 3 | 按钮 loading 抖动(忽闪) | 快速并发请求,前一个的 `finally` 把后一个的 loading 提前清掉 | useRequest 已通过 `controllerRef.current === controller` 防抖,无需手动处理 |
| 4 | manual 模式下页面加载就发了空请求 | 没传 `{ manual: true }`,走了自动模式 | 默认是自动模式(`manual: false`),触发型场景**必须显式传 manual** |
| 5 | 错误既走 message.error 又被业务 try/catch 二次处理 | 沿用旧代码的 try/catch 习惯 | 删掉 try/catch,用 `if (data === undefined) return` 短路(contract 3) |
| 6 | service 内 `.then` 报 "Cannot read property of undefined" | 接口返回的 data 是 null / 错误结构 | 在 service 内做防御:`.then(data => data ?? [])`,或在调用方 `data?.foo` |
| 7 | hook data 是 `null` 想用默认值 | 没设初始态(hook 用 `useState(null)`) | 调用方用 `data || defaultValue` / `data?.field ?? ''` |
| 8 | 切 tab 回来重新请求 | 当前 hook 不缓存,每次都新请求 | 设计稿决策**不做缓存**,需要时再引 SWR / react-query |

## 五、迁移老 view 的步骤(checklist)

把一个老 view 从 `try/await` 模式迁到 useRequest:

- [ ] **1. 改 import**:`request` → `api` + `useRequest`(`api` 走 axios signal 通道,`request` 不支持)
- [ ] **2. 包 service**:如果 refetch 会进 useCallback deps,用 `useCallback([])` 包 service
- [ ] **3. 替换调用**:`try { request.post(...) } catch` → `await refetch(...)` + `if (data === undefined) return`
- [ ] **4. 接 loading**:按钮 `loading={loading}`,并存按钮 `disabled={loading}`
- [ ] **5. 删死状态**:原来 `useState` 存"set 但不读"的字段,删掉(hook 内部已托管)
- [ ] **6. 删 console.error**:hook 已统一 message.error,业务代码不再处理已知错误
- [ ] **7. 跑一遍**:`npm run dev`,DevTools Network 看 Authorization header 仍在;Console 无 unmounted 警告;loading 反馈正常

每个 view **一个 commit**,小步前进,便于 `git bisect`。

## 六、何时考虑下一步抽象

### 触发器:service 集中化(Markdown/视图处理方式设计.md 阶段 3)

只有当**至少 2 处复用同一个 service** 时才抽到 `src/services/`。例如:

```js
// src/services/user.js
import { api } from '../server/request';
export const fetchUser = (params, { signal }) => api.get('user', { params, signal });

// view A
import { fetchUser } from '../../services/user';
const service = useCallback(fetchUser, []);
const { data } = useRequest(service);

// view B 同样用 fetchUser,只导入不重复定义
```

**反模式**:只在一个 view 用还要抽 service —— 没收益,纯多文件成本。

### 触发器:引入缓存层

当出现以下任意一项,考虑引入 SWR / react-query:
- 切 tab / 回到上一页时数据"闪一下白屏",体验差
- 多个 view 调同一接口,重复请求浪费带宽
- 需要乐观更新(mutation) / 失败自动重试

**当前不做**——4 个 demo 没有任何上述场景。
