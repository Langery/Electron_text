## 一、背景与现状

### 现状盘点(基于 view 分支)

通过 `git grep` 静态分析,view 层有 4 处直接发请求 + 1 处用了 props 回调,模式分散:

| View | 数据获取方式 | 错误处理 | Loading 状态 | 状态管理 |
|------|------------|----------|------------|---------|
| `Login/login.js` | `try/await` 在 `onFinish` 内 | `console.error` | 无(无 loading 提示) | `useState('large')` |
| `Register/register.js` | `try/await` 在 `onFinish` 内 | `console.error` | 无 | `useState × 2` |
| `MainView/components/indexview.js` | `useEffect` + `fetch().then()` | `console.error` | 无 | `useState × 2` |
| `Pages/mainpage.js` | `useCallback` 包裹 async | `console.error` | 无 | `useState × 5` |
| `Pages/dragpage.js` | 无网络请求(纯前端) | — | — | `useState/useRef` |
| `Home/home.js` | 无 | — | — | 无 |
| `demo/demopage.js` | 待查 | | | |

### 5 个具体痛点

1. **重复样板**: 每个 view 都有"loading/try-catch/setState"三件套,代码 80% 雷同
2. **Loading 状态缺失**: 用户点击提交后**没有视觉反馈**(按钮不变灰、不能再次点击)
3. **请求竞态**: `useEffect` 里的 `fetch` 组件卸载后还在 setState,会触发 React 警告
4. **状态耦合**: UI 状态(`size`、`clearData`)和数据状态(`firstData`)混在同一个 useState 列表里
5. **没有缓存**: 同一接口多次调用(比如切 tab 后再回来)会重复请求

## 二、目标

按重要性排序:

1. **消除重复**: 一个 `useRequest` hook 覆盖 80% 的 fetch 场景
2. **Loading 显式化**: UI 必须能区分"加载中"和"已完成"两态
3. **请求安全**: 组件卸载时自动 abort 飞行中的请求
4. **状态分层**: UI 状态 / 数据状态 / 表单状态 分别管理
5. **缓存可选**: 简单场景不带缓存,需要时按需加(不强制)

非目标(本轮**不做**):
- 不上状态管理库(Redux/zustand/jotai),useState + useReducer 够用
- 不做 SSR 适配(项目是 Electron 桌面应用)
- 不做完整的缓存/失效机制(留给未来需要时再设计)
- 不改 view 文件夹的物理结构(只引入新的 hook/容器概念)

## 三、设计原则

| 原则 | 说明 |
|------|------|
| **最小抽象** | 不引入任何 npm 新包(react-query/swr/zustand 等),全用 React 18 + 项目已有依赖 |
| **渐进迁移** | 不强制一次性全量改写,新 view 按新模式写、老 view 保持运行;逐步替换 |
| **可逆性** | 如果 `useRequest` 不够用,退回原来 `useEffect+fetch` 也不增加复杂度 |
| **约定优先** | 命名/位置/导出风格统一,靠 code review 维持(不上 lint 规则) |

## 四、核心抽象

### 抽象 1:`useRequest` 自定义 Hook

**位置**: `src/hooks/useRequest.js`

**签名**:
```js
useRequest(serviceFn, options) => {
  data,        // any | null
  error,       // Error | null
  loading,     // boolean
  refetch,     // () => Promise
  abort        // () => void
}
```

**`serviceFn`**: 一个返回 Promise 的函数,例如:
```js
const fetchUser = (params) => request.get('getUserInfo', params);
const { data, loading } = useRequest(fetchUser, { id: 1 });
```

**`options`**:
- `manual: true` —— 不在 mount 时自动调用,改用 `refetch()` 触发
- `deps: []` —— 依赖变化时重新调用(类似 useEffect deps),默认 `[]`
- `onSuccess/onError` —— 回调

**自动行为**:
- 组件卸载时 `abort()` 取消飞行中的请求(用 `AbortController` + axios signal)
- 同一组件并发调用时,前一个请求被自动 abort(避免竞态)
- `loading` 初始为 `true`(若自动调用)或 `false`(若 `manual`)

**示例(伪代码,展示期望行为)**:
```jsx
function UserProfile({ userId }) {
  const { data, loading, error, refetch } = useRequest(
    (params) => request.get('getUserInfo', params),
    { userId }   // deps 变化时自动重新请求
  );

  if (loading) return <Spin />;
  if (error) return <Alert message={error.message} type="error" />;
  return <div>{data?.name}</div>;
}
```

### 抽象 2:View 三层划分(可选,不强求)

**位置**: 在 `view/<Page>/` 目录内文件命名约定

| 层级 | 后缀 | 职责 | 例子 |
|------|------|------|------|
| **Page 入口** | `*.page.jsx` | 路由组件,只做组合 | `Login.page.jsx` |
| **Container** | `*.container.jsx` | 数据层,调用 `useRequest` | `Login.container.jsx` |
| **View/UI** | `*.view.jsx` 或同名 | 纯展示,接 props | `Login.view.jsx` |

**不强制拆分**——如果一个 view 简单到不需要,可以保持单文件;只有当单个文件 > 200 行或多人协作时再拆。

### 抽象 3:Service 集中化(可选)

**位置**: `src/services/` 目录

每个 endpoint 一个文件,导出对应的 service 函数:

```js
// src/services/user.js
import { request } from '../server/request';
export const getUserInfo = (params) => request.get('getUserInfo', params);
export const login = (data) => request.post('login', data);
export const register = (data) => request.post('register', data);
```

**好处**: service 函数可以在多个 view 复用,接口路径集中管理。

**非强制**: 简单 view 可以在 useRequest 里写 inline arrow function,不需要先建 service 文件。

## 七、风险与权衡

| 风险 | 缓解 |
|------|------|
| `useRequest` 抽象过早,后期变瓶颈 | 保持 `useRequest` 极简(~80 行),不做 SWR/react-query 的全功能 |
| 老 view 不迁移,形成两种风格并存 | 明确"新 view 用新模式,老 view 不强制改";在重构指南里说明 |
| `AbortController` 在 axios 老版本不支持 | 项目用 axios 1.6.7,完全支持 |
| Loading 状态从无到有,UI 突然多出 spinner 可能影响视觉 | 用 antd `Spin` 组件,只在容器层包裹,样式可统一调 |
| 引入新目录 `hooks/` `services/` 后 src 结构变深 | 在 `Markdown/README.md` 索引里加新目录说明 |

## 九、未决问题(等用户决策)

1. **`useRequest` 是否要支持缓存?**
   - 简单版: 不支持(每次都是新请求)
   - 进阶版: 支持 `cacheKey` 去重(类似 SWR 的 dedupe-interval)
   - 建议: **不做**,等真有需求再扩

2. **是否同时改 `request.js` 让它支持 AbortController?**
   - 简单版: `useRequest` 内部自己包一层 axios 调用,直接传 signal
   - 进阶版: 改 `request.js` 让每个方法接收 signal 参数
   - 建议: **前者**,不改 `request.js`(职责单一)

3. **是否在阶段 1 同步加 ErrorBoundary 触发的 toast?**
   - 现有 `src/common/ErrorBoundary.jsx`(D 组已加)只在 UI 树顶层兜底
   - `useRequest` 内部 error 是已知错误,走 `message.error` 而不是 ErrorBoundary
   - 建议: **保持现状**,ErrorBoundary 兜未知错误,`useRequest` 走已知错误

4. **`.prettierrc` 是否要在阶段 1 一起跑一遍格式化?**
   - 现在 `useRequest.js` 是新文件,可以直接按 `.prettierrc` 风格写
   - 老文件不动(避免大 diff)
   - 建议: **新文件遵守,老文件不动**
