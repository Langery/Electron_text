| # | 项 | 文件 | 说明 |
|---|----|------|------|
| 1 | 新增 `<LibraryOverview />` 组件 | `src/view/components/libraryOverview.jsx` | lazy 读 localStorage;header 含标题 + 刷新按钮;Empty 状态(用 UserAddOutlined 图标);grid 自适应(`repeat(auto-fill, minmax(220px, 1fr))`) |

**Grid 自适应**

```less
grid-template-columns: repeat(auto-fill, minmax(220px, 1fr));
```

- 视口宽 → 多列(4+ 列)
- 中等宽 → 2-3 列
- 窄(< 600px)→ 1 列

**为什么用 auto-fill 而不是固定 grid**

- nav1 是响应式布局(xs/sm/md/lg);auto-fill 让卡片数自动跟随容器宽度
- 固定 4 列在窄屏会挤,固定 2 列在大屏会空 —— auto-fill 是中间最优解

**为什么 Empty 用 UserAddOutlined 而非默认图**

- 默认 Empty 图是个简单矩形,语义不直观
- UserAddOutlined(加号 + 人头)直接表达"去加新人"的引导意图
- 配 description "点上方「新增」表单填好后 + 加入备选库" 指明操作路径

**为什么是 Lazy + 手动刷新(跟 L-B / O 组一致)**

- 同款跨页 localStorage pattern:L-B dragpage library、O 组 chartxkcd 都是这个模式
- 三处共用一致的 UX:**数据来自 storage,改动需手动刷新**
- 没引 `storage`事件监听,因为同 tab 内不触发,反而需要自定义事件总线,得不偿失

**未触动的行为**

- nav2-nav6 完全不变
- OperationSelf 4+1 按钮不变
- 表单"加入备选库"流程不变 —— 仍写 localStorage,只是多了个 mainpage 端的可见性

```
│ [Demo 数据] [备选库数据]   [刷新]  │  ← Radio.Group + 刷新按钮

│                                   │
│           <Line chart>            │  ← 动态 config
│                                   │

```

- 选 Demo → 渲染原硬编码数据
- 选备选库 → 渲染 candidateLibrary 中有效项(name + age);空时显示 Empty 占位

**关键设计取舍**

**1. 为什么过滤而非回退到 0**

- chart.xkcd 收到 `data: [undefined, undefined]` 会渲染异常
- `isValidItem` 严格过滤 `name && age > 0`,Empty 状态兜底没有效数据的场景
- 不做"没填 age 就当 0"是因为 0 在年龄语义里是错的(婴儿?数据缺失?)

**2. 为什么用 Radio.Button 而非 Select**

- 仅 2 个选项,Radio.Button 横排展示 + 当前选中态可见,比 Select 一行折叠更适合切换频繁的 demo 场景
- antd Radio.Button 在小尺寸下样式紧凑(`size="small"`)

**3. 为什么手动"刷新"按钮**

- 跟 dragpage library 的 pattern 一致 —— 跨页 localStorage 同步只能手动
- `storage`事件监听不解决同 tab 内的跨组件同步问题(只在跨 tab 时触发)
- 代价是用户多一步,但更可控

**4. 为什么不持久化 source 选择**

- O 组保持会话期(跟 M 组 tab 系统同策略)
- 用户刷新后回到 demo 默认,符合"新打开看 demo"的直觉
- MVP 阶段不暴露 setSource 持久化接口

**未触动的行为**

- DEMO_CONFIG 保持原样,只移到模块顶层做常量化(原来在组件内)
- nav5 里 chartxkcd 仍跟 map / rough 一起 3 列排列
- L组 / N组 的其他流程不动

## 2026-06-10 view 分支 N 组 阶段A:dragpage 布局持久化(单 commit)

**目的**:实现 dragpage 画布状态的跨会话持久化(单 slot MVP,无版本管理)。给画布布局一个"保存 / 清空"入口,数据写 `localStorage.dragLayout`,on-mount 自动加载。给 N-B mainpage"恢复布局"按钮提供数据基础。

**改动范围**:1 个文件

| # | 项 | 文件 | 说明 |
|---|----|------|------|
| 1 | 加 `readDragLayout` / `persistDragLayout` 模块级工具 | `dragpage.js` | 同 L-B `readCandidateLibrary` 模式;try/catch 包裹 parse / setItem |
| 2 | `rightDragList` 改 lazy initializer | `dragpage.js` | `useState(() => readDragLayout())` —— 挂载时一次读 localStorage;不是 useEffect(避免初始 render 闪空) |
| 3 | 加 `saveLayout` / `clearLayout` callback | `dragpage.js` | save = `persistDragLayout(rightDragList)` + `message.success`;clear = `setRightDragList([])` + 清 storage + toast |
| 4 | 加"保存布局" / "清空布局" 按钮到 operatio_zone | `dragpage.js` | 紧跟现有"Reset List";clear 按钮 `disabled={rightDragList.length === 0}` |

**为什么用 lazy initializer 不用 useEffect**

- `useState(() => readDragLayout())` 在第一次 render 之前就执行,初始状态就是 storage 里的值
- 用 `useEffect(() => { ... })` 会先 `useState([])` 空 → render 空画布 → useEffect 触发 → setState → 再 render 有内容,中间会闪一下"空画布"
- lazy initializer 避免这个闪烁

**为什么只支持单 slot 不支持多版本**

- L组 candidateLibrary 是列表(multiple items),dragLayout 是整体布局(single canvas state)—— 语义不同
- MVP 单 slot 已能验证 localStorage 持久化模式
- 多版本管理(thumbnails / 命名 / 时间戳)是后续 P2,本阶段不做

**未触动的行为**

- `leftDragList` / `candidateList` 的初始化和持久化方式不变
- "Reset List" 按钮只重置 in-memory state,**不写 localStorage** —— 跟"清空布局"语义不同:Reset 是"回到默认菜单项 + 空画布",清空布局是"清空画布并删除持久化"
- 拖拽 / 排序 / 库项渲染等既有逻辑不变

## 2026-06-10 view 分支 M 组:卫星导航多页签系统(单 commit)

**目的**:实现 README idea 章节长期挂 `[ ]` 的"路由 > 卫星导航"。现有路由跳转是全屏替换模式 —— 从 mainpage 跳 dragpage 后,mainpage 的 nav state、detailInfor、备选库 Modal 状态等全部丢失。本组把每个路由封装为可保留的 tab,切换不卸载组件 → state 全部保留。同时把 README 的"卫星导航"勾掉。

**改动范围**:4 个文件(3 新 + 1 改)

| # | 项 | 文件 | 说明 |
|---|----|------|------|
| 1 | 新增 `TabsProvider` + `useTabs` hook | `src/contexts/TabsContext.jsx` | React Context,提供 `tabs / activeKey / openTab / closeTab / switchTab`,跟项目内 `useRequest` hook 风格一致 |
| 2 | 新增 `<TabBar />` | `src/view/components/TabBar.jsx` | 基于 antd `Tabs type="editable-card"`,自带 × 关闭 + 横向 overflow scroll + active 样式,免去自定义 UI |

**核心数据流**

```
URL 变化 (useLocation)
  ↓ TabsSyncer useEffect
openTab(path)
  ↓
setTabs (去重添加) + setActiveKey
  ↓
TabBar 重渲染 (antd Tabs 新增 item)

closeTab(key)
  ↓
setTabs (过滤 + 兜底补 Home) + setActiveKey (切到剩余第一个)
  ↓ TabsSyncer 第二个 useEffect
navigate(activeKey)
  ↓
URL 变化 → 触发第一个 useEffect → openTab(已存在,跳过)
```

**PATH_TITLES 硬编码映射**

| path | title |
|------|-------|
| `/` | Home |
| `/login` | Login |
| `/register` | Register |
| `/mainpage` | Main |
| `/dragpage` | Drag |
| `/demo` | Demo |

**path 规范化**

- 全部 tab key 用规范化后的 path

**关键边界**

- Home tab (`/`) `closable: false` —— 兜底保证至少 1 个 tab;`closeTab('/')` 早退不响应
- 关闭所有 tab 后 setTabs 兜底补一个 Home;activeKey 切到 `/`;URL 导航到 `/`
- 访问不存在的路由 `/foo`:`openTab` 内 `isTabable` 早退;Route 不渲染;tab bar 不变
- 刷新页面:tab 列表重置(会话期),URL 保留,TabsSyncer 从 URL 重新开当前路径的 tab

**没引新依赖**

- antd 已在项目内,Tabs 组件 0 增量
- 不引 zustand/redux 等状态库,Context 够用

**不动的东西**

- 任何路由页面(mainpage/dragpage/login/register/home/demo)逻辑不变 —— 它们继续 `navigate()` 和 `<Link>`,TabsSyncer 自动同步
- AuthBridge / useRequest / request.js 原样

```js
  const t = setTimeout(() => {
    setPage(1);                       // 搜索时跳第 1 页, 避免"第 5 页搜词只剩 3 页"
```

3. **abort 语义统一**:`refetch` 返回 `undefined` 表示"被 abort 或已 toast 的错误",调用方据此判断是否继续业务流程(见 Login `if (data === undefined) return`)。
4. **loading 清理防抖**:`finally` 里只在 `controllerRef.current === controller` 时清 loading,避免快速并发中"上一个请求的 finally 把新请求的 loading 提前清掉"。

### 二、统一请求层(request.js 重写 + view 迁移)

**改动前**
- `src/server/request.js` 只是"请求准备函数",返回 `[url, options]` 元组
- 每个 view 各自 `await fetch(url, options)` + `response.json()` + 重复的错误处理

**改动后**
- `src/server/request.js` 用 axios 单例 + 拦截器封装,导出 `request.get/post/put/delete`
- 请求拦截器:从 `localStorage` 自动注入 `Authorization: Bearer <token>`
- 响应拦截器:统一返回 `data`,401 自动清 token 跳登录页,统一抛 `{code, message, url}` 错误
- 4 个 view 全部从 `PostWay` / `GetWay` / 手写 `fetch` 迁移到 `request.post(...)` / `request.get(...)`

**修改文件**
- `src/server/request.js` — 完全重写
- `src/view/Login/login.js` — `PostWay` + `fetch` → `request.post()`
- `src/view/Register/register.js` — `PostWay` + `fetch` → `request.post()`
- `src/view/Pages/mainpage.js` — `GetWay` + `fetch` → `request.get()`
- `src/view/MainView/components/indexview.js` — `PostWay` + `fetch` → `request.post()`

**收益**
- view 代码量减少 ~30%(每个请求从 3 行变 1 行)
- 401 处理从"每个 view 写一遍"变成"拦截器一处生效"
- 新增页面时不用再写 fetch 样板

### 三、错误日志(Electron IPC + 主进程写文件)

**目的**:捕获渲染进程未处理错误,写入用户数据目录,便于事后排查。

**改动**
- 新增 `src/utils/logger.js`:监听 `window.error` / `unhandledrejection`,通过 `window.electronAPI.writeErrorLog` 发送到主进程;dev 环境 fallback 到 `console.error`
- 新增 `electron/main.js` IPC 句柄 `write-error-log`:在 `app.whenReady().then()` 内部注册(与现有 `ping` 一致),将日志追加写入 `app.getPath('userData')/logs/error.log`(macOS 是 `~/Library/Application Support/electron-ant/logs/error.log`)
- 新增 `electron/preload.js` `writeErrorLog` API,经 `contextBridge` 暴露到 `window.electronAPI`
- 新增 `src/index.js` import `./utils/logger`,让监听器在应用启动时挂载
- 导出 `logger.error/warn/info` 给业务侧主动调用

**顺带修复**
- `electron/main.js` 顶层的 `win?.webContents.on('render-process-gone', ...)` / `'did-fail-load'` 在 `win` 还未赋值时已运行,监听**实际从未生效**。本次新增的 IPC 句柄都放在 `app.whenReady().then()` 内部,符合既有注册位置。`render-process-gone` / `did-fail-load` 监听暂未迁移(超出本次范围,后续单独 commit)。

**日志格式**
```
[2026-06-08T03:14:25.123Z] [UNHANDLED_REJECTION] TypeError: ...
[2026-06-08T03:14:25.456Z] [JS_ERROR] ReferenceError: ...
[2026-06-08T03:14:25.789Z] [ERROR] LoginContext: 用户名不存在
```

**修改文件**
- `src/utils/logger.js` — 新建
- `electron/main.js` — 加 `fs` import + `write-error-log` IPC 句柄
- `electron/preload.js` — 加 `writeErrorLog` 暴露
- `src/index.js` — 加 `import './utils/logger'`
- `Markdown/修改内容.md` — 本节
