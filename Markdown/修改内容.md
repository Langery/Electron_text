## 2026-06-12 view 分支 V-A 组:dragpage 选中态视觉强化(单 commit)

**目的**:T-A 把 InfoPage 从 stub 升级成真实详情面板,但**画布上被选中的元素本身没有视觉反馈**。点击 `right_item` → InfoPage 跳出新内容,画布上对应元素仍是默认外观,信息流是断的(用户视线在两处切换)。本轮把"选中态"反向同步到画布,让选中信息**单一来源**(都是 `selectedItem.id`)、**视觉集中**(用户一眼锁定当前在编辑哪个元素)。

**改动范围**:2 个文件(1 改 dragpage + 1 改 drag.less)

| # | 项 | 文件 | 说明 |
|---|----|------|------|
| 1 | SumSide 加 `selectedId` prop | `src/view/Pages/dragpage.js` | `SumSide` 接收 `selectedId`;map 时 `const isSelected = selectedId != null && item.id === selectedId;`;className 拼接 `right_item${isSelected ? ' selected' : ''}`;调用处传 `selectedId={selectedItem?.id}`(可选链,初始 null 不 NRE) |
| 2 | `.right_item.selected` 样式 | `src/style/drag.less` | 默认 `border: 2px solid transparent` 占位(避免切换时 width 跳动);selected 态 `border-color: #1890ff` + `box-shadow: 0 0 0 2px rgba(24, 144, 255, 0.15)`;`transition: 0.15s` 缓动 |

**选中态与拖动 over 共存设计**

| 状态 | class | 视觉 |
|------|-------|------|
| 选中 | `.right_item.selected` | 蓝色 2px 边框 + 蓝色光晕 |
| 拖动 over 容器 | `.right-wrap.over` | 红色 2px 边框 + 浅红背景 |
| 选中 + 拖动 over(同时) | 两个 class 共存 | 蓝色 + 红色叠加(都生效,无 CSS 冲突) |

两个 class 选不同颜色是为了**角色分离**:蓝=静态选中,红=动态拖动目标。用户在拖一个已选中项时,两种视觉同时出现,**反而强化了"我正在操作这个元素"**的反馈,不会冲突。

**为什么用 `border-color` + `box-shadow` 而不是 `outline`**

- `outline` 不占布局空间(原本占,但 layout 影响小),但 `outline-offset` 不能配合 border-radius 一起用,而 dragpage 画布上的元素(Button/Input)有圆角
- `box-shadow` 不影响 layout,圆角自适应,且可以用 `rgba` 半透明实现"光晕"效果,更现代
- 选 `box-shadow: 0 0 0 2px rgba(...)` 而非 `box-shadow: 0 0 8px` —— 前者跟 border 一样"实",后者是"模糊光晕"。dragpage 是工作区,**实边框 + 光晕**比**模糊发光**更精确

**为什么用 `transparent` 占位边框**

未选中时也写 `border: 2px solid transparent`,选中时切到 `#1890ff` —— 切换时元素 width 不会跳 2px。`transparent` 边框有渲染体积,跟 `solid` 边框占位等效,但视觉上不可见。

**验证**:`npx vite build` ✓(`built in 32.52s`,exit 0)。dev 启起来 → dragpage 拖几个元素到中间 → 点其中一个 → 该元素出现蓝色边框 + 光晕,InfoPage 同步显示详情 → 点另一个 → 蓝色边框移动到新元素 → 拖动某元素到画布上时,画布外框是红色,内部已选中元素保持蓝色,两种状态独立显示。

**为什么"切换主题"和"清空备选库"是 useMemo 派生项**

- 切换主题:title 文案跟当前 theme 联动(`settings.theme === 'dark' ? '切换到浅色主题' : '切换到深色主题'`),放硬编码会过期
- 清空备选库:项数为 0 时不该出现在列表里(无意义),用 useMemo 自动按 `library.length` 决定是否注入

**快捷键设计**

| 场景 | 监听位置 | 处理 |
|------|----------|------|
| 调出/关闭命令面板 | `window` 上 keydown | `(metaKey \|\| ctrlKey) && key === 'k'`,`e.preventDefault()` 防 Firefox 聚焦搜索框 |
| Modal 内导航 | `<Input onKeyDown>` | ↑↓ 切 hoverIndex(循环);Enter 执行;Esc 关 |
| 打开时聚焦 Input | `useEffect[open]` 50ms 后 `inputRef.current.focus()` | antd Modal 动画期间不能立即 focus,setTimeout 让位 |

**为什么用 `useMemo` 派生 `commands` 而不是 `useState + useEffect`**:不存任何状态,只根据 props(theme, library.length)计算。如果用 useEffect 同步,会多一帧延迟,还得多写一个 useState 镜像。useMemo 在每次 render 时返回新数组对 memo 没影响(因为 CommandPalette 自身被 memo 包裹,commands 不进 props)。

**确认 Modal 设计**:清空是**不可逆操作**,必须二次确认(避免误触 Cmd+K → 输入"清" → Enter 立刻把 100 项数据删了)。但其它命令(跳转、切主题)都**幂等/可逆**,直接执行。

**为什么 `useNavigate` 就够,不需要 `useTabs.openTab`**:`<TabsSyncer>`(在 App.js 已有)监听 `location.pathname` 变化自动调 `openTab`,所以命令面板只需要 `navigate(path)`,tab 系统自动同步。

**目的**:U-A2 把排序 + 上限接到 LibraryOverview,本轮把第三个高频交互「搜索」也补上,使备选库总览在 100+ 项时仍可定位目标。3 个派生层叠 `useMemo`:`items → sortLibrary().slice(cap) → filter(keyword)`,每层只在自己依赖变化时重算。

| # | 项 | 文件 | 说明 |

**3 个 useMemo 派生链**

| 层 | 输入 | 输出 | 依赖 |
|----|------|------|------|
| L1 | `items`(localStorage 原始值) | `displayItems = sortLibrary(items, settings.librarySort).slice(0, settings.libraryMaxItems)` | `items`, `settings.librarySort`, `settings.libraryMaxItems` |
| L2 | L1 + `keyword` | `searchedItems = L1.filter(matchesKeyword)` | `displayItems`, `keyword` |
| L3 | L2 | 渲染网格(本次) / 描述文案(本次) | — |

每层只重算自己依赖,搜索输入触发 L2 重算,L1 不动(不重新排序),`items` 变(新增/删除/编辑)才重排+重过滤。

**为什么 keyword 不持久化**:搜索是**当下探查意图**,刷页就该清空。和 `useLocalStorage('appSettings')`(用户偏好,跨页持久)与 `useLocalStorage('candidateLibrary')`(业务数据,跨页持久)形成对比。

**为什么用 `Input` + `prefix` 而非 `Search` antd 组件**:Search 会自带搜索按钮 + onSearch 回调(典型表单提交场景),而这里想要的是"边输边过滤"的实时搜索。普通 `Input` + 受控 `value` + `onChange` 模式更轻量,也不需要按钮。

**空态拆分 UX 考虑**

| 状态 | image | description | 用户感知 |
|------|-------|-------------|----------|
| 无数据 | `<UserAddOutlined style="fontSize:48,color:'#d9d9d9' />` | "还没有备选项,点上方「新增」表单填好后 + 加入备选库" | 引导去 mainpage 添加 |
| 有数据但无匹配 | `Empty.PRESENTED_IMAGE_SIMPLE` | "没有匹配「{keyword}」的候选项" | 提示换个关键词 |
| 有结果 | — | 网格 + 描述文案 | 正常浏览 |

| 2 | `rightDragList` 改 lazy initializer | `dragpage.js` | `useState(() => readDragLayout())` —— 挂载时一次读 localStorage;不是 useEffect(避免初始 render 闪空) |

**为什么用 lazy initializer 不用 useEffect**

- `useState(() => readDragLayout())` 在第一次 render 之前就执行,初始状态就是 storage 里的值

- lazy initializer 避免这个闪烁

**为什么只支持单 slot 不支持多版本**

- L组 candidateLibrary 是列表(multiple items),dragLayout 是整体布局(single canvas state)—— 语义不同
- MVP 单 slot 已能验证 localStorage 持久化模式
- 多版本管理(thumbnails / 命名 / 时间戳)是后续 P2,本阶段不做

**未触动的行为**

- `leftDragList` / `candidateList` 的初始化和持久化方式不变
- "Reset List" 按钮只重置 in-memory state,**不写 localStorage** —— 跟"清空布局"语义不同:Reset 是"回到默认菜单项 + 空画布",清空布局是"清空画布并删除持久化"
- 拖拽 / 排序 / 库项渲染等既有逻辑不变

  const t = setTimeout(() => {
    setPage(1);                       // 搜索时跳第 1 页, 避免"第 5 页搜词只剩 3 页"

3. **abort 语义统一**:`refetch` 返回 `undefined` 表示"被 abort 或已 toast 的错误",调用方据此判断是否继续业务流程(见 Login `if (data === undefined) return`)。
4. **loading 清理防抖**:`finally` 里只在 `controllerRef.current === controller` 时清 loading,避免快速并发中"上一个请求的 finally 把新请求的 loading 提前清掉"。

### 二、统一请求层(request.js 重写 + view 迁移)

**改动前**
- `src/server/request.js` 只是"请求准备函数",返回 `[url, options]` 元组
- 每个 view 各自 `await fetch(url, options)` + `response.json()` + 重复的错误处理

**改动后**
- `src/server/request.js` 用 axios 单例 + 拦截器封装,导出 `request.get/post/put/delete`
- 请求拦截器:从 `localStorage` 自动注入 `Authorization: Bearer <token>`
- 响应拦截器:统一返回 `data`,401 自动清 token 跳登录页,统一抛 `{code, message, url}` 错误
- 4 个 view 全部从 `PostWay` / `GetWay` / 手写 `fetch` 迁移到 `request.post(...)` / `request.get(...)`

**修改文件**
- `src/server/request.js` — 完全重写
- `src/view/Login/login.js` — `PostWay` + `fetch` → `request.post()`
- `src/view/Register/register.js` — `PostWay` + `fetch` → `request.post()`
- `src/view/Pages/mainpage.js` — `GetWay` + `fetch` → `request.get()`
- `src/view/MainView/components/indexview.js` — `PostWay` + `fetch` → `request.post()`

**收益**
- view 代码量减少 ~30%(每个请求从 3 行变 1 行)
- 401 处理从"每个 view 写一遍"变成"拦截器一处生效"
- 新增页面时不用再写 fetch 样板

### 三、错误日志(Electron IPC + 主进程写文件)

**目的**:捕获渲染进程未处理错误,写入用户数据目录,便于事后排查。

**改动**
- 新增 `src/utils/logger.js`:监听 `window.error` / `unhandledrejection`,通过 `window.electronAPI.writeErrorLog` 发送到主进程;dev 环境 fallback 到 `console.error`
- 新增 `electron/main.js` IPC 句柄 `write-error-log`:在 `app.whenReady().then()` 内部注册(与现有 `ping` 一致),将日志追加写入 `app.getPath('userData')/logs/error.log`(macOS 是 `~/Library/Application Support/electron-ant/logs/error.log`)
- 新增 `electron/preload.js` `writeErrorLog` API,经 `contextBridge` 暴露到 `window.electronAPI`
- 新增 `src/index.js` import `./utils/logger`,让监听器在应用启动时挂载
- 导出 `logger.error/warn/info` 给业务侧主动调用

**顺带修复**
- `electron/main.js` 顶层的 `win?.webContents.on('render-process-gone', ...)` / `'did-fail-load'` 在 `win` 还未赋值时已运行,监听**实际从未生效**。本次新增的 IPC 句柄都放在 `app.whenReady().then()` 内部,符合既有注册位置。`render-process-gone` / `did-fail-load` 监听暂未迁移(超出本次范围,后续单独 commit)。

**日志格式**
```
[2026-06-08T03:14:25.123Z] [UNHANDLED_REJECTION] TypeError: ...
[2026-06-08T03:14:25.456Z] [JS_ERROR] ReferenceError: ...
[2026-06-08T03:14:25.789Z] [ERROR] LoginContext: 用户名不存在
```

**修改文件**
- `src/utils/logger.js` — 新建
- `electron/main.js` — 加 `fs` import + `write-error-log` IPC 句柄
- `electron/preload.js` — 加 `writeErrorLog` 暴露
- `src/index.js` — 加 `import './utils/logger'`
- `Markdown/修改内容.md` — 本节
